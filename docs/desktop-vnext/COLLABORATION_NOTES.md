# AutoSlice 协作与执行规则

> 作用：记录用户与 ChatGPT、Work、Remote Desktop Commander 协作时已经形成的实际规则，减少以后重复确认和误操作。

## 1. 总体工作方式

默认流程：
1. 先讨论目标、边界和产品行为。
2. 用户明确说“开始做 / 可以改 / work / 弄吧”等之后，再进入实现。
3. 如果用户只说“先探讨”，不要直接发 Work 或改代码。
4. 实现完成后，先看真实结果，再决定是否继续下一阶段。
5. 不因为自动化测试通过就强行宣布体验问题解决。

用户曾明确纠正过：
> “先探讨，没让你直接 work。”

因此讨论阶段和执行阶段必须区分。

## 2. Remote Desktop Commander 优先场景

用户偏好：
> Remote Desktop Commander 能用就用，不要浪费额度。

优先用 Remote Desktop Commander：
- 读取本地仓库文件；
- 写项目文档；
- 小范围配置调整；
- 文件整理；
- 本地目录盘点；
- 简单命令和验证；
- 用户明确说“用 Remote Desktop Commander”时。

不要为了写一份 Markdown、看一个目录或做很小的本地文件修改就启动高额度 Work。

## 3. Work 适合的场景

Work 适合：
- 跨多个代码文件的大批次实现；
- 架构审查；
- 大范围测试和 Qt 实机验证；
- 长时间分析；
- 用户准备睡觉，希望利用额度做一批工作；
- 用户明确要求“直接 Work”。

Work 任务要有边界：
- 明确改哪些；
- 明确不改哪些；
- 明确是否允许 commit/push；
- 明确验收方式；
- 不让 Work 自由扩展成“顺便重构整个仓库”。## 4. 用户授权和节奏

当需要 Work 交接时：
- 必须等待用户在 UI 中允许；
- 如果用户忘记点允许，应明确说明任务尚未开始；
- 不要把“准备好任务”说成“已经在执行”。

如果用户说“继续”：
- 已有明确冻结范围时，可以继续下一步分析；
- 如果下一步涉及代码修改，仍应确认当前是否已经明确进入执行阶段；
- 用户明确“work / 开始 / 弄”时，可以直接交执行。

## 5. Git 规则

默认：
- 不 commit；
- 不 push；
- 不 force push；
- 不改 Git 历史。

只有用户明确要求时才提交或推送。

重要分支语境：
- `desktop-vnext-dev`：当前桌面开发主线。
- `desktop-vnext-preview`：旧稳定预览基线，禁止覆盖。
- 其他 UI 实验分支只作参考，不能直接把行为冲突代码合入当前主线。

执行前应先查看当前工作区，避免覆盖：
- 既有未提交修改；
- 未跟踪 `work/`；
- 其他模型/用户产生的改动。

## 6. 文档规则

Desktop vNext 当前唯一文档入口：
`docs/desktop-vnext/README.md`

当前状态、规范和决策优先写进当前有效文档，不继续往历史阶段计划追加“当前状态”。

历史文件：
- 保留；
- 不删除；
- 放入 `archive/`；
- 只用于追溯。

长期项目记忆文档：
- PROJECT_CONTEXT.md
- USER_REQUIREMENTS.md
- INTERACTION_CONTRACT.md
- COLLABORATION_NOTES.md
- HISTORY_AND_LESSONS.md

这些文件用于“inherit project state, not chat history”。## 7. 代码修改规则

不要为了架构整洁机械拆文件。

优先级：
1. 修真实用户问题。
2. 守住已冻结交互。
3. 保持模块边界。
4. 再考虑结构美化。

特别约束：
- 不把新业务状态机继续塞进 `DesktopWindow`。
- 字幕模块稳定后，不为了统一风格重写。
- AutoCover 的新能力应落在独立 model/service/controller/canvas owner。
- CoverDraft 只做兼容，不恢复为主模型。
- 异步任务必须考虑 generation/token。

## 8. 用户反馈处理方式

用户会直接给截图并评价：
- “一坨”
- “很怪”
- “拖动卡”
- “文案根本不能用”

这类反馈应该转换成具体可验证问题，而不是辩解。

例如：
- “拖动一坨” → profile mouseMove 链路、是否重渲染/重保存；
- “文字怪” → 字体来源、WYSIWYG、样式迁移、实际 bbox；
- “文案没用” → 检查 A/B 语义和 golden set；
- “界面很怪” → 信息架构、画布占比、上下文面板是否堆叠。

如果真实截图与报告中的“视觉通过”冲突，以截图为准。

## 9. 测试和验收用语

允许说：
- “技术检查通过”
- “69 tests passed”
- “Qt 入口启动成功”

不应仅凭这些说：
- “视觉验收通过”
- “产品已经可用”
- “问题已经解决”

视觉/产品结论需要用户实际测试或明确的真实人工验收证据。## 10. 高算力模型的使用

高算力 Work 应主要用于：
- 系统性代码审查；
- 多文件实现；
- 深度旧版对比；
- 回归测试；
- 长链路问题定位。

不要让高算力模型：
- 凭空替用户设计审美；
- 为了“更先进”抛弃旧版已经好用的行为；
- 用大量新抽象掩盖交互问题。

旧版 AutoCover 是“功能矿和行为基线”，不是 UI 目标，但用户已经认可的交互要优先复刻。

## 11. AI 成本意识

用户额度敏感。

开发和产品共同原则：
- 本地规则能解决就本地解决；
- 不做无效 AI 调用；
- 模型请求应缓存；
- 基础功能不依赖 AI；
- 真实 AI relay 接入前先把编辑器本身做顺。

## 12. 文件安全

不要删除：
- `work/`；
- 不认识的本地文件；
- 用户源视频；
- 原始 SRT；
- 既有导出成片。

文件整理时：
- 优先移动到 archive；
- 不做破坏性清理；
- 不因为“看起来没用”就删未跟踪文件。

## 13. 结束一次工作时应报告

至少说明：
- 改了哪些文件；
- 实现了什么；
- 没有做什么；
- 跑了哪些技术检查；
- 已知问题；
- 是否 commit/push；
- 下一步建议。

如果只是写文档，就不要启动服务、FFmpeg 或真实 AI 做无关验证。
