# AutoCover UX-04：编辑器基础模型架构规划

> 模型版本：v2。
> 
> 状态：前置架构规划，仅分析和写计划，未修改业务代码、未启动服务、未调用外部 LLM、未提交、未 push。
> 
> 审查基线：2026-10-02，`src/autoslice/desktop/cover.py`、`cover_canvas.py`、`cover_service.py`、`tests/unit/test_desktop_cover.py` 和 `docs/desktop-vnext/AUTOCOVER_UX_AUDIT.md`。

## 1. 这次要解决什么

AutoCover 的目标是让速切用户在几分钟内完成一张可发布封面：从当前播放头附近选一帧，得到一个可用的封面钩子，快速调整构图，然后导出。它不需要成为 Photoshop、Canva 或完整的海报排版工具。

UX-03 已经修复了若干表层契约：4:3/16:9 主画布切换、标题按下偏移、背景拖动方向、自动保存、异步渲染代际保护和当前比例导出。这些变化可以保留。但继续在现有 `CoverCanvas` 的坐标逻辑上加功能，会把每个新需求都变成一组互相同步的字段、信号和临时判断。UX-04 的任务是先建立一个能承载真实编辑行为的模型，再逐阶段把交互接回去。

本计划只定义模型、职责、迁移路径和实现顺序。它不要求现在修改 `cover.py`、`cover_canvas.py`、`cover_service.py` 或字幕代码。

## 2. 当前模型为什么会持续产生问题

### 2.1 背景构图差：模型只有“图片 + 焦点”，没有构图对象

当前 `CoverDraft`（`cover_service.py:20-69`）把背景表示成 `image_path`、`background_x`、`background_y` 和 `background_scale`。这些字段表达的是“用一张图按某个焦点裁切”，没有表达：

- 图片在当前画布中的可见矩形；
- 图片和画布的适配方式是填满、适合还是保留比例留边；
- 平移是在可用溢出范围内如何移动；
- 需要避开的主体、人物、原图文字或字幕区域；
- 4:3 与 16:9 是否需要不同取景。

渲染器随后用 `ImageOps.fit` 和焦点裁切（`src/autoslice_cover/renderer.py:507-567`）。`CoverService.suggest_text_position()` 只在四个固定槽位上计算边缘能量（`cover_service.py:194-244`）。边缘越多不等于越适合放字：人物轮廓、商品界面、原图文字和字幕都会增加边缘能量。于是算法可能把标题放到视觉信息最密集的区域，用户只能再手动救回来。

当前默认 `background_x/background_y=0.5`、`background_scale=1.0`，只提供居中填充和焦点微调。它没有“左边内容、右边人物”“人物在上方、标题在下方”等可解释的构图关系，也没有把自动结果作为一个可调整的布局建议保存。因此截图中的背景问题不是某个默认坐标偏了，而是模型没有保存或计算构图意图。

### 2.2 文本框不像编辑器：字符串被当成了对象

当前标题在模型中只有 `CoverDraft.title`、`text_x`、`text_y` 和 `font_size`。`cover.py:_update_title_rect()` 根据近似字符宽度临时算出一个 `QRectF`，再传给 `CoverCanvas`；真正渲染时，`cover_service.text_transforms_for()` 把每一行转换成多个 `TextTransform`（`cover_service.py:98-111`）。这个流程存在三个不同的“文字形状”：输入框里的字符串、画布上的临时矩形、渲染器里的逐行布局，它们没有共同的对象身份。

因此当前模型无法稳定表达：

- 一个文字对象自己的宽度、高度和最小/最大尺寸；
- 自动换行的最大宽度、行距和对齐方式；
- 填充、描边、描边宽度、阴影、字体等样式；
- 文字对象和未来第二个文字对象之间的层级与独立位置；
- 文字换行后边界框如何变化，以及缩放时保持什么约束。

右侧 `QPlainTextEdit` 只是编辑字符串，画布不是真正的文本编辑器。画布显示四角控制点，但当前 `CoverCanvas` 没有控制点命中、拖动缩放或最小尺寸计算（`cover_canvas.py:298-306` 只负责绘制）。所以用户拖的是一个由外层代码拼出来的字符串矩形，而不是一个有几何、样式和生命周期的文字对象。

### 2.3 拖动和缩放体验差：视图、草稿和渲染状态相互拉扯

`CoverCanvas` 目前继承 `QLabel`，自己维护 `_title_rect`、`_selected_object`、背景焦点、缩放值和当前手势模式（`cover_canvas.py:14-47`）。`CoverEditorWidget` 又维护 `CoverDraft`，并在每个信号回调里调用 `_read_draft()`、`replace()`、更新控件、启动保存和启动预览（`cover.py:580-632`）。这产生了几类状态耦合：

1. 画布的矩形是从草稿和当前输入框临时推导的，拖动时又反向写回多个控件。
2. 背景拖动改变的是归一化焦点，不是一个明确的图片变换或裁切框；“填满”和“适合”目前实际都调用同一个重置方法（`cover.py:637-642`）。
3. 标题缩放没有交互路径，字号变化会重新估算矩形；换行、字号和位置不能作为同一次编辑操作提交或撤销。
4. 预览是异步生成的栅格图片，画布上的标题框是另一套即时几何。随着文字换行或比例切换，这两套状态可能出现短暂或长期不一致。
5. 点击标题以外的区域默认进入背景拖动（`cover_canvas.py:176-205`），选择、移动背景和调整裁切没有清晰的模式边界。

UX-03 的按下偏移修复是必要的，但它只修复了“拖动起点”这个局部错误。继续增加缩放、对齐、多个文字块或图片元素时，当前类会继续膨胀为手势状态机、渲染状态机和草稿同步器的混合体。

### 2.4 继续打补丁会失控：缺少稳定的领域边界

当前职责分布大致是：

| 位置 | 实际承担的职责 | 继续扩展的结果 |
| --- | --- | --- |
| `cover.py` | Qt 布局、草稿字段同步、异步任务、预览生命周期、导出、文字矩形推导 | 每增加一个对象字段，就要增加控件、信号、`replace()` 和保存/预览分支 |
| `cover_canvas.py` | QLabel 绘制、图片显示、命中判断、标题拖动、背景平移、吸附、选择反馈 | 文字缩放、多个对象、层级和裁切会全部塞进一个控件 |
| `cover_service.py` | 扁平草稿序列化、候选文案、取帧、构图建议、预览和导出 | 服务既要理解 UI 坐标，又要理解渲染器和未来对象模型 |
| `renderer.py` | 模板排版、逐行文字变换、背景适配、最终栅格输出 | UI 的每个新对象都需要额外拼接成旧式参数，模型语义不断丢失 |

缺少的是一个可序列化、可测试、与 Qt 无关的 `CoverDocument`。没有它，以下功能都会重复造轮子：选择、拖动、缩放、自动换行、两个比例各自调整、自动构图、撤销/重做和 AI 建议应用。

### 2.5 现有测试证明了可靠性底线，却没有证明编辑器模型

`tests/unit/test_desktop_cover.py` 当前覆盖了几条应该保留的底线：草稿私有存储往返、媒体取帧、预览/导出尺寸、递增文件名、4:3/16:9 输出、按下偏移拖动和标题/背景选择信号。它们能防止 UX-03 的明显回归，但测试对象仍是 `CoverDraft` 字段、Qt 信号和单标题矩形。

现有测试没有验证：

- 两个独立文字对象或一个对象的宽度/高度缩放；
- 对象内部左/中/右对齐、样式和自动换行后的稳定边界；
- 背景 fit/contain、可用溢出范围、裁切框和明确的取景模式；
- 同一对象在两个 profile 中独立覆盖并往返保存；
- 对象命中顺序、z-index、撤销/重做和异步文档代际；
- 自动构图是否避开真实截图中的人物、界面文字和字幕。

因此不能以当前测试全绿作为“编辑器已经建立”的证据。UX-04 需要先建立模型层契约测试，再把 Qt 交互测试绑定到对象命令和文档快照。

## 3. UX-04 的目标边界

### 3.1 要建立的边界

采用三层结构：

1. **领域模型**：只描述封面文档、对象、比例配置和可恢复状态，不依赖 PySide6。
2. **编辑器控制器/画布适配层**：把鼠标和键盘手势转换成对象命令，负责选中、命中、拖动、缩放、吸附和撤销/重做。
3. **服务与渲染适配层**：负责取帧、资产缓存、草稿读写、异步预览和导出；把领域模型转换成现有渲染器可以消费的布局。

`CoverEditorWidget` 仍然是 Qt 页面入口，但不再拥有文字或背景的业务几何；`CoverCanvas` 仍然是 Qt 控件，但不再直接维护业务草稿字段。

### 3.2 明确不做的事情

- AutoCover 不做 Photoshop/Canva 替代品：不引入复杂图层面板、蒙版、贝塞尔路径、复杂滤镜、动画或模板市场；底层对象仍需保留移动、缩放、旋转和层级能力，避免过早限制后续素材类型。
- 不改字幕工作流、字幕草稿、字幕预览和 `DesktopWindow` 的页面切换契约。
- 不把旧版独立 `CoverWorkspace`、目录扫描、标题 Markdown 或旧队列重新接回 vNext 主入口。
- 不在模型重建阶段同时接真实 AI、素材库、批量导出或自动上传。
- 不把“自动构图建议”变成强制锁定；用户始终可以直接拖动和微调。

## 4. 新的编辑模型

下面的字段是语义契约，不要求按原样命名或一次全部实现。实现时应优先采用不可变值对象和显式版本号，避免把 Qt 类型写入草稿。

### 4.1 `CoverDocument`：封面文档根对象

建议新增纯 Python 模型模块，例如 `src/autoslice/desktop/cover_model.py`。根对象负责文档身份和对象集合：

对象集合按职责分为五类：

```text
CoverDocument

├── BackgroundObject   # 主背景、取景和裁切
├── TextObject         # 标题、钩子和说明文字
├── ImageObject        # 人物、截图和一般图片素材
├── StickerObject      # 表情、箭头和反应素材
└── ShapeObject        # 圆圈、箭头和矩形强调框
```

```python
CoverDocument(
    version=4,
    source=SourceRef(video_id, selected_timestamp, image_asset_id),
    profiles={"4x3": LayoutProfile(...), "16x9": LayoutProfile(...)},
    objects=(BackgroundObject(...), TextObject(...)),
    active_profile="4x3",
    selected_object_id="title-main",
)
```

根对象的约束：

- 对象使用稳定 `id`，不能用列表下标作为身份。
- 对象有 `kind`、`transform`、`z_index`、`visible` 和 `locked` 等最小通用字段。`kind` 至少覆盖 `background`、`text`、`image`、`sticker` 和 `shape` 五类；第一版 UI 可以只启用 `background` 与 `text`，但序列化和渲染适配器不能因此把其他类型排除在模型之外。
- 所有可渲染对象共享一套基础变换语义：

  ```python
  Transform(
      x=0.5,
      y=0.5,
      scale=1.0,
      rotation=0.0,
  )
  ```

  `x/y` 使用归一化画布坐标，`scale` 表示对象相对基础尺寸的缩放，`rotation` 使用角度。文字对象的 `rect` 表达局部宽高，位置由 `transform.x/y` 表达；背景的裁切和平移、图片的透明度等仍由各对象的专属字段表达，它们不能改变通用变换字段的含义。
- 对象的基础值与比例覆盖分开保存。没有覆盖时使用基础值；有覆盖时只覆盖该比例需要变化的字段。
- 选中对象、活动比例和最后成功预览属于可恢复编辑状态，但不应影响渲染结果。
- 所有坐标使用与画布无关的归一化矩形或明确的变换值；Qt 的像素矩形只存在于视图适配层。

AutoCover 不做 Photoshop 替代品。底层对象要保留移动、缩放、旋转、层级和未来扩展所需的能力，但 UI 不提供复杂图层面板，也不要求用户理解专业图层操作。

领域模型不保存字体测量后的像素行框。换行结果、实际字体回退和最终像素边界属于渲染阶段的派生数据。

### 4.2 `TextObject`：真正的文字对象

建议的最小语义：

```python
TextObject(
    id="title-main",
    text="事件、悬念或反应",
    rect=Rect(x=0.0, y=0.0, width=0.58, height=0.30),
    transform=Transform(x=0.08, y=0.16, scale=1.0, rotation=0.0),
    wrap=TextWrap(max_width=0.58, mode="wrap", max_lines=3),
    align="left",                 # left | center | right
    style=TextStyle(
        font_family="...",
        font_size=104,
        fill="#FFFFFF",
        stroke="#111111",
        stroke_width=6,
        shadow=True,
        line_spacing=1.12,
    ),
    z_index=10,
)
```

必须支持的行为：

- **选择**：点击可见文字区域命中对象；选中对象有边界框和最小控制点反馈。
- **拖动**：记录按下点相对对象矩形左上角的偏移，移动时只改变 `transform.x/y`（或当前 profile 的对应覆盖）；不能因为点击文字中部而跳位。
- **缩放**：拖动四角控制点改变 `rect.width/height`，遵守最小字号/最小矩形约束；是否保持比例由文字对象规则决定，不能把缩放误当成背景缩放。
- **自动换行**：根据对象宽度、字体和 `max_lines` 派生行；用户手动换行必须保留，自动换行不能破坏显式换行。
- **样式**：填充、描边、描边宽度、阴影、字体、字号和行距属于对象样式，而不是散落在页面控件和渲染器默认值里。
- **对齐**：对齐是对象框内的 `left/center/right`，不是通过修改每一行的绝对 `x` 来伪装。对象移动与对象内部对齐必须是两件事。
- **派生布局**：渲染器根据同一个 `TextObject` 计算行、实际字体和像素边界；画布使用同一测量器或同一布局结果画选中框，避免“输入框、画布框、导出框”三套尺寸。

`TextObject` 必须保留 `rotation` 字段并在序列化中往返，即使默认编辑 UI 不强制暴露旋转控件。第一版可以把它固定为 `0`，或只允许后续命令/API 写入；这不应阻止模型为未来的轻量倾斜标题保留扩展空间。第一版仍不需要路径文字、逐字样式或复杂富文本，不能把速切主流程变成排版软件。

### 4.3 `BackgroundObject`：图片、缩放、平移、裁切

背景应成为一个明确的对象，而不是几个散落在 `CoverDraft` 上的字段：

```python
BackgroundObject(
    id="background-main",
    asset=AssetRef(path="...", asset_id="..."),
    fit_mode="cover",             # cover | contain
    scale=1.0,                     # 相对基础适配结果
    pan_x=0.0,                     # 可用溢出范围中的归一化平移
    pan_y=0.0,
    crop=CropRect(...),            # 可选；没有自定义裁切时由 fit + pan 派生
    z_index=0,
)
```

语义要求：

- `asset` 只引用私有缓存中的图片或取帧资产；导入、复制和路径安全仍由 `CoverService` 负责。
- `fit_mode` 明确区分填满画布和适合画布。源图与目标比例不同时，是否留边、使用背景衬底或裁切由渲染适配器解释。
- `scale` 表示相对基础适配结果的缩放，不是一个无法解释的 UI 百分比。
- `pan_x/pan_y` 表示拖动方向与画面移动方向一致的平移；控制器负责把鼠标位移映射到可用溢出范围。
- `crop` 是可恢复的裁切语义。初期可由 `fit_mode + scale + pan` 推导；当用户进入明确的裁切模式后再持久化自定义裁切矩形。
- 背景默认只在“调整取景”模式中响应拖动，避免点击空白区域时误把背景移动。用户必须能看到当前处于选择背景还是调整取景。

这个对象不要求第一版实现滤镜、模糊、亮度、蒙版或背景生成。它只把“图片应该怎样进入画布”说清楚。

### 4.4 `ImageObject`：人物、截图和一般图片素材

`ImageObject` 用于承载不属于主背景的图片，例如人物抠图、网页截图、商品图或用户导入的素材。它与背景共用对象身份和变换语义，但不负责画布底色和全画布裁切：

```python
ImageObject(
    id="host-cutout",
    asset=AssetRef(path="...", asset_id="..."),
    transform=Transform(x=0.72, y=0.52, scale=0.62, rotation=-6.0),
    opacity=1.0,
    crop=CropRect(...),
    z_index=20,
)
```

职责和边界：

- 支持移动、缩放、裁剪、透明度和旋转；旋转是明确的一等能力，因为直播切片封面常需要轻微倾斜来制造动势或区分素材。
- `asset` 只引用经过 `CoverService` 导入和缓存的资源；对象不直接负责文件复制、路径安全或解码。
- 图片对象默认按自身边界参与命中和绘制，不改变背景的 fit/contain 语义。
- 第一版不做抠图、蒙版、复杂滤镜或图片内部编辑；这些属于资源处理能力，不应混入编辑模型。

### 4.5 `StickerObject`：贴纸、表情和反应素材

`StickerObject` 面向速切封面中高频使用的轻量素材。它可以复用 `ImageObject` 的资源和变换字段，但增加可检索、可统计的分类语义：

```python
StickerObject(
    id="reaction-wow",
    asset=AssetRef(path="...", asset_id="..."),
    category="reaction",       # reaction | arrow | emoji | effect
    transform=Transform(x=0.84, y=0.22, scale=0.24, rotation=12.0),
    opacity=1.0,
    z_index=30,
)
```

能力范围：

- 支持移动、缩放、旋转和透明度；旋转不能被素材库或 UI 的默认模板限制为 0。
- `category`、`reaction` 等标签只服务于素材选择和未来推荐，不改变渲染器对图片资源的基本处理。
- 不做完整素材市场、时间轴动画或复杂特效编辑；素材库应通过稳定 `asset_id` 接入。

### 4.6 `ShapeObject`：少量强调图形

`ShapeObject` 用于标注和强调，不承担通用矢量绘图职责。第一版只定义三种形状：

- `circle`：圈出人物、按钮或画面细节；
- `arrow`：指向关键区域；
- `rect`：矩形强调框。

```python
ShapeObject(
    id="focus-ring",
    shape_type="circle",
    transform=Transform(x=0.56, y=0.46, scale=0.30, rotation=0.0),
    style=ShapeStyle(fill=None, stroke="#FFDB4D", stroke_width=8),
    z_index=25,
)
```

形状对象支持基础填充、描边、描边宽度和通用变换；箭头与矩形可以旋转，圆圈通常保持 `rotation=0`。不做贝塞尔路径、渐变节点、布尔运算或复杂图层效果，避免把速切编辑器推向专业矢量工具。

### 4.7 `LayoutProfile`：4:3、16:9 与比例覆盖

比例不是一个全局 `canvas_key` 加一套共享坐标，而是文档中的两个明确输出配置：

```python
LayoutProfile(
    key="4x3",
    width=1440,
    height=1080,
    safe_area=SafeArea(...),
    overrides={
        "background-main": ObjectOverride(...),
        "title-main": ObjectOverride(rect=Rect(...)),
    },
    export_suffix="",
)
```

设计规则：

- 4:3 与 16:9 都是可导出的真实 profile；“另一比例预览”只是视图层的检查方式，不是数据模型。
- 新建文档时用基础对象生成两个 profile；切换后允许独立修改文字位置、文字框宽度、背景取景和必要的字号/样式。
- 只有用户实际修改的字段进入 `overrides`。这样既能共享同一套对象和文案，又不会把 4:3 的位置强行套到 16:9。
- 若用户选择“同步一次”，执行的是显式复制当前值的命令；之后两个 profile 仍然可以独立编辑。
- 导出调用必须接收 `profile_key`，并由 profile 提供尺寸和命名后缀。不能再让服务层默认猜 4:3。

### 4.8 交互状态与命令

选择态、拖动中的临时状态和撤销历史不应写进任何对象本身：

- `SelectionState`：当前对象 id、当前控制点、hover 对象和是否显示辅助线。它可以作为 `CoverDocument` 的可恢复编辑元数据保存，但不能进入对象的渲染字段。
- `GestureState`：按下位置、按下时对象快照、对象局部偏移、当前 profile 和手势类型。
- `EditCommand`：移动、缩放、改文字、改样式、换背景、改取景、切换 profile；每个命令可生成前后文档状态。
- `History`：在一次拖动结束时提交一个命令，拖动过程只更新预览；撤销/重做不需要知道 Qt 控件。

对象仍应有稳定 `z_index`，渲染顺序和命中顺序必须明确。第一版不需要复杂的图层面板，至少要能通过对象命令或简单上下文操作调整前后关系，为图片、贴纸和形状留下接口。

### 4.9 `CoverLayoutEngine`：默认布局与未来 AI 构图接口

`CoverLayoutEngine` 是独立的布局领域服务，负责把背景主体、输出比例和对象关系转成可解释的初始布局建议。它不直接修改 `CoverDocument`，也不依赖 Qt 控件：

```python
LayoutSuggestion(
    profile="16x9",
    background=BackgroundPlacement(...),
    object_overrides={
        "title-main": ObjectOverride(...),
        "host-cutout": ObjectOverride(...),
    },
    reason="人物位于右侧，左侧留白适合标题",
    confidence=0.82,
)
```

输入至少包括：

- 背景主体、人物、界面、原图文字和字幕风险等分析结果；
- 目标比例、画布安全区和输出尺寸；
- 现有对象之间的关系，例如“标题避开人物”“贴纸靠近被强调区域”。

输出包括背景的 fit/scale/pan/crop 初值、对象的 `transform` 或矩形覆盖、建议原因和置信度。引擎可以由 `CompositionAnalyzer` 提供确定性证据，也可以在未来接收 AI 生成的候选；无论来源是什么，最终都必须落成同一个 `LayoutSuggestion`，由用户预览、调整或撤销。

默认构图始终是建议，不是锁定规则。分析失败或置信度低时，`CoverLayoutEngine` 应回退到兼容布局并允许继续编辑，不能阻塞导出。

## 5. 新旧模型的职责映射

| 领域能力 | UX-04 的归属 | 当前代码处理方式 | 迁移结论 |
| --- | --- | --- | --- |
| 文字内容/框/样式/换行 | `TextObject` + 文本测量器 | `CoverDraft` 标题字段、`wrap_cover_title()`、逐行 `TextTransform` | 保留文字测量和字体回退，改为从对象布局适配到旧渲染器 |
| 背景图片/取景 | `BackgroundObject` | `image_path`、焦点和缩放字段 | 保留私有资产缓存和取帧，统一变换语义 |
| 人物/截图/图片素材 | `ImageObject` | 当前没有独立对象 | 新增资源引用、透明度、裁剪和可旋转变换；第一版可先由适配器渲染 |
| 表情/箭头/反应素材 | `StickerObject` | 当前没有独立对象 | 复用图片资源能力，增加分类标签和可旋转变换 |
| 圆圈/箭头/强调框 | `ShapeObject` | 当前没有独立对象 | 只实现三种基础形状，不引入复杂矢量编辑 |
| 比例输出 | `LayoutProfile` | `_canvas_key` + 共享 `CoverDraft` | 保留尺寸和文件命名契约，新增每 profile 覆盖 |
| 画布命中/手势 | Canvas controller | `CoverCanvas` 内部判断标题否则背景 | 拆出对象命中、拖动、缩放和模式状态 |
| 自动构图 | `CoverLayoutEngine` + `CompositionAnalyzer` + `LayoutSuggestion` | 四槽位边缘能量评分 | 由布局引擎综合主体、比例和对象关系，输出可解释、可撤销的建议 |
| 草稿恢复 | `CoverDocument` 序列化适配 | `CoverDraft.to_payload()` 版本 1~3 | 增加版本 4 读取迁移；旧版本可回退为一个背景对象和一个文字对象 |
| 取帧/导入/导出 | `CoverService` I/O | 已有服务方法 | 保留异步和递增文件名，只改变输入从 draft 变为 document/profile |
| 项目和字幕页联动 | `CoverEditorWidget` 公共入口 | `set_context()`、`set_current_playhead()` | 保持方法和信号契约，不让模型依赖字幕实现 |

## 6. 迁移方案：保留、拆分与淘汰

### 6.1 必须保留的可靠基础

- `SubmissionProject`、`ProjectVideo` 和 `DesktopStorage`，继续作为投稿上下文、视频来源和私有持久化边界。
- `CoverService` 中的私有图片缓存、真实视频取帧、附近帧提取、异步可调用方法和递增导出文件名。
- 预览与导出使用同一渲染路径的原则；现有“同一变换状态下预览与导出字节一致”的测试继续作为回归基线。
- `cover_copy.py` 的确定性候选作为无字幕上下文时的稳定回退，不把它误包装成完整语义理解。
- `DesktopWindow` 与字幕页之间的 `set_context()`、只读播放头交接和页面切换行为。
- 当前版本的 generation/dirty 保护思想：异步结果必须带文档/profile 代际，旧结果不能覆盖新编辑状态。

### 6.2 应拆出的新模块职责

建议按职责逐步新增，而不是先重写所有文件：

- `cover_model.py`：`CoverDocument`、五类对象、`Transform`、`LayoutProfile`、值对象、版本化 payload。
- `cover_layout.py`：文本测量、自动换行、对象边界、profile 覆盖合并和 `CoverLayoutEngine` 的布局结果。纯 Python，可脱离 Qt 测试。
- `cover_commands.py`：移动、缩放、改字、改样式、取景和 profile 操作；后续承载撤销/重做。
- `cover_composition.py`：从图片统计中生成若干 `LayoutSuggestion`，供 `CoverLayoutEngine` 消费；不直接修改文档，不调用 AI。
- `cover_canvas.py`：逐步变成视图适配器，负责绘制渲染结果、对象框、控制点和辅助线，并把鼠标事件交给控制器。

模块可以先放在 `src/autoslice/desktop/`，不要为 UX-04 新建第二套服务或重新接旧版 `CoverWorkspace`。

### 6.3 应逐步收缩的旧职责

- `CoverDraft` 先保留为兼容 DTO 和迁移入口，不能再作为新增功能的主模型。所有新字段不得继续追加到它上面。
- `cover.py` 保留 Qt 页面、任务排队和状态提示，但逐步删除 `_read_draft()` 驱动的逐字段同步、`_update_title_rect()` 的业务计算和标题/背景信号分支。
- `cover_canvas.py` 删除“点击标题否则背景”的隐含业务规则；旧信号可以在过渡期继续发出，但来源改为对象命令结果。
- `cover_service.py` 保留文件和媒体 I/O；渲染调用改为“文档 + profile → 渲染适配器”，不再由服务拼接单标题逐行变换。
- `render_cover()` 保留为兼容底层渲染器入口；新增文档渲染适配器把对象模型转换成现有 `TextTransform`、背景参数和未来扩展对象，避免一次性改写稳定渲染器。

### 6.4 旧草稿迁移

迁移只在读取时发生，写入新版本后不覆盖用户原有媒体：

1. 读取版本 1~3 的 `CoverDraft` payload。
2. `image_path` 转成一个 `BackgroundObject`；`background_x/y/scale` 转成兼容的 `pan/scale` 初始值。
3. `title/text_x/text_y/font_size` 转成一个 `TextObject`；宽度和高度用现有换行测量器计算一次作为初始矩形。
4. 建立 `4x3` 和 `16x9` 两个 profile：先复制兼容值，再允许用户分别调整。
5. 在新文档成功保存后写入版本 4；迁移失败时保留旧 payload 并显示可执行错误，不删除草稿。

迁移适配器必须有纯数据测试。不要在迁移阶段自动重新分析整条视频，也不要让字幕工作流为封面模型提供反向依赖。

## 7. 实现顺序

每个阶段都应能单独验证，阶段之间不以“把所有功能一次接通”为完成条件。

### Phase 1：基础对象

**目标**：领域模型能表达包含五类对象的封面文档，并能保存、恢复、渲染；第一阶段的页面交互仍可只启用背景和一个文字对象。

**工作项**：

1. 建立 `CoverDocument`、五类对象、通用 `Transform`、`LayoutProfile` 和版本化 payload；先让 `ImageObject`、`StickerObject`、`ShapeObject` 可以被序列化和渲染适配器识别。
2. 建立旧 `CoverDraft` → 新文档的读取适配，以及新文档 → 旧渲染器参数的适配。
3. 把文本换行、对象矩形和 profile 覆盖定义成无 UI 的纯函数。
4. 保持当前 Qt 页面可用：先由适配器生成旧画布需要的矩形和服务参数，不改字幕/`DesktopWindow`。

**验收**：

- 版本 1~3 草稿可以恢复为一个背景对象和一个文字对象；新草稿保存为新版本。
- 新模型可以往返保存五类对象的 `id`、`z_index`、`transform` 和对象专属字段；旧草稿迁移时没有额外素材也不会虚构图片、贴纸或形状对象。
- 4:3/16:9 都能从同一文档渲染，切换 profile 不污染另一个 profile 的覆盖值。
- 预览与导出仍走同一适配器，已有私有缓存和递增命名契约不变。
- 运行模型、迁移和渲染适配器的纯单元测试；不启动服务、不调用 LLM、不修改字幕测试。

### Phase 2：画布交互

**目标**：用户操作的是对象，而不是散落的坐标参数。

**工作项**：

1. 将 `CoverCanvas` 改为文档视图：根据对象布局绘制选中框、控制点、背景取景边界和辅助线。
2. 实现对象命中、选择、拖动、文字框缩放和背景调整取景模式；拖动使用按下偏移，缩放使用最小尺寸和边界约束，图片与贴纸保留旋转手势/API。
3. 增加 `EditCommand` 和最小撤销/重做历史；一次完整拖动只产生一个可撤销命令。
4. 继续使用自动保存和异步预览，但保存/渲染输入改为文档快照和 profile 代际。

**验收**：

- 点击文字任何位置拖动都不跳；拖动后文字框的相对偏移保持。
- 拖四角控制点能改变文字框宽度/高度，换行和对齐随对象框更新；拖背景只在明确的取景模式中改变图片。
- 4:3 与 16:9 可以分别拖动同一文字对象，切换回来位置保持。
- 图片和贴纸对象的旋转值可以保存、恢复并参与预览/导出；默认 UI 可以把该能力放在轻量上下文操作中。
- Qt offscreen 测试覆盖命中、拖动、缩放、背景取景、选择态和撤销；不依赖真实媒体。

### Phase 3：默认构图

**目标**：新草稿首次打开就有一个较合理的构图，减少用户救图时间；自动结果是建议，不是锁。

**工作项**：

1. 新增 `CoverLayoutEngine` 和 `CompositionAnalyzer`：分析器提供确定性证据，布局引擎输出候选 `LayoutSuggestion`，不直接写入 UI 字段。
2. 在不调用 AI 的前提下，组合以下确定性证据：区域边缘/纹理密度、亮度和对比度、明显大块文字/字幕风险、源图比例与可见主体分布。
3. 对 4:3/16:9 分别生成少量关系明确的候选：左内容右人物、右内容左人物、上方主体下方标题、中部留白等；给出“为什么选择该区域”的简短原因和置信度。
4. 背景对象根据 profile 使用独立的填充/裁切/平移初值；标题对象根据可用区域生成矩形和字号，不再只从四个固定槽位挑最低边缘能量。
5. 首屏只展示一个默认建议和一个轻量切换入口，始终允许直接拖动调整。

**验收**：

- 对包含人物、商品/界面和原图文字的代表性样本，默认标题不再稳定压在信息最密集区域。
- 自动构图失败或置信度低时安全回退到兼容布局，并明确显示“可手动调整”，不阻塞封面编辑。
- 构图分析是离线、可测试、可重复的；不启动外部服务、不调用 LLM。
- 用真实截图样本做离线黄金集验证，覆盖 4:3 和 16:9；不要以单色测试图代替构图验收。

### Phase 4：文案钩子

**目标**：让用户从少量候选中快速选出事件、悬念或反应，而不是继续强化标题拆分器。

**工作项**：

1. 定义候选输入契约：投稿标题、当前选帧时间附近的校对字幕/片段上下文、缺少上下文时的回退说明。
2. 保留 `basic_hook_variants()` 作为确定性回退；候选应用动作只更新 `TextObject.text`，不重建整个文档。
3. 将候选应用、手动改文案、自动换行和文字样式变化纳入同一套命令/自动保存路径。
4. 仍不调用 AI；把未来 AI 入口设计成显式的“给我几个建议”，不在打开封面或输入文字时后台调用。

**验收**：

- 标题很长但没有结果词、结果只出现在字幕、缺少字幕三类输入都有可解释的候选或回退。
- 用户选定候选后可以直接拖动、缩放和对齐；文案变化不重置背景取景。
- 测试覆盖候选服务、应用命令、自动换行和 profile 独立布局。

### Phase 5：AI 辅助

**目标**：在稳定编辑模型上提供可控的建议，进一步减少找帧、提炼文案和初始构图时间。

**工作项**：

1. AI 只能由用户明确触发，输入范围与隐私边界在服务契约中写清楚。
2. 一次返回少量候选（优先 3 个），每个候选带简短理由；默认只预览，不自动改文档。
3. AI 建议应用为可撤销命令，可以只应用文字、只应用构图或同时应用两者。
4. 缓存按视频/字幕上下文/文档版本区分；失败时回退 Phase 3/4 的确定性建议。

**验收**：

- 无 AI 配置、请求失败或用户不点击时，主流程仍能完成封面。
- 不产生隐藏的付费调用；测试使用 mock，不向真实服务发送请求。
- AI 不绕过对象模型、不写入字幕状态、不改变 `DesktopWindow` 页面契约。

## 8. 测试与验收策略

### 8.1 模型层

- 版本化序列化/反序列化、旧草稿迁移、非法值边界和 profile 覆盖合并。
- 五类对象的通用 `Transform`、`z_index`、可见性/锁定字段和对象专属字段的往返；`TextObject.rotation` 即使默认 UI 隐藏也必须保留。
- 文本对象的显式换行、自动换行、最大行数、对齐和矩形边界。
- 背景对象的 fit/scale/pan/crop 语义，尤其是拖动方向与可用溢出范围。
- 文档快照相等性、命令前后状态和撤销/重做。

### 8.2 画布层

- offscreen Qt 测试命中顺序、选择态、按下偏移、四角缩放、背景取景模式、辅助线和 profile 切换。
- 不把“有信号发出”当作交互通过；断言对象的矩形、样式或取景状态确实按预期变化。
- 真实媒体集成测试只验证取帧、预览、导出链路，不把长录播或整场压制带入 AutoCover 验收。

### 8.3 构图与视觉验收

- 建立包含人物、界面、原图文字、左右主体和不同源图比例的离线黄金集。
- 每个样本检查：默认标题是否避开主要信息、人物是否被不必要地裁掉、4:3/16:9 是否各自可读、文字是否越界。
- 允许人工调整并记录“建议是否被接受、调整了多少”；不要只用单元测试证明“算法运行了”。

### 8.4 回归边界

每个阶段完成后，都应确认以下接口没有改变：

- `CoverEditorWidget.set_context(project, video)`；
- `CoverEditorWidget.set_current_playhead(seconds)` 的只读交接语义；
- `DesktopWindow` 的项目/页面选择和字幕状态；
- 字幕生成、校对、预览、保存和压制流程；
- 现有私有草稿、媒体缓存和导出文件不被删除或覆盖。

| 新模型与旧渲染器语义不一致 | 预览与导出边界或文字位置不同 | Phase 1 必须通过同一适配器字节/像素契约 | 保留 `CoverDraft` 读取和旧渲染入口，只回退 UI 适配 |
| 4:3/16:9 覆盖污染 | 切换比例后另一比例位置跟着变化 | 每个 profile 的覆盖有独立 round-trip 测试 | 只写基础值，暂时隐藏独立覆盖入口 |
| 构图建议误判主体 | 标题频繁落在人物/界面/原图文字上 | 黄金集接受率低于人工可接受阈值时不进入默认流程 | 回退兼容布局并把建议改成显式候选 |
| Qt 交互再次变成字段同步 | 新增一个对象属性需要多个 widget 信号 | Phase 2 所有交互先生成命令，再由文档驱动视图 | 暂停新控件，只完善模型和命令测试 |
| 异步旧结果覆盖新编辑 | 快速切换帧/比例后预览回退 | 回调携带 document/profile generation | 丢弃旧回调，不修改当前草稿 |
| 速切流程变慢 | 进入封面后等待或需要理解更多控件 | 以“选帧→钩子→调整→导出”的点击数和等待时间验收 | 隐藏低频面板，保留一键回退布局 |

## 10. UX-04 完成定义

UX-04 前置架构只有在以下条件同时成立时，才可以进入实现后的体验验收：

1. `CoverDocument` 能独立描述背景、文字、图片、贴纸、形状和 4:3/16:9 profile，不依赖 Qt 控件；所有对象共享明确的 `transform`、`z_index` 和选择态边界。
2. 旧草稿可以安全迁移，新草稿保存有明确版本；预览和导出仍共享渲染适配器。
3. 画布交互以对象命令为中心，选择、拖动、缩放、换行、对齐和背景取景不再靠 `CoverDraft` 字段互相追写。
4. `CoverLayoutEngine` 生成的默认构图是可解释、可回退、可手动调整的建议，能够针对代表性真实截图避开主要主体和高信息区域，并为未来 AI 提供同一建议接口。
5. 文案钩子、AI、字幕系统和 `DesktopWindow` 都通过明确边界接入；没有为了完成模型而扩大产品范围。
6. 实现阶段仍遵守速切预算：用户无需学习专业设计术语，能在少量操作内得到并导出一张可发布封面。

这份计划取代“继续给 `cover_canvas.py` 增加坐标分支”的方向，但不要求现在删除或回滚 UX-03 的工作。下一步若开始实现，应从 Phase 1 的纯模型和迁移测试开始，并在每个阶段完成后再进入下一阶段。
